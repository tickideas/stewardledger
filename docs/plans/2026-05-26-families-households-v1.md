# Families / households v1 — implementation plan

Date: 2026-05-26
Branch (proposed): `feat/families-households`
Phase: 10 — Billing & GA exit-checklist item *"Family / household grouping"*.
Reference: [`docs/CHURCHPLUS-PORT-NOTES.md` §2.2.1](../CHURCHPLUS-PORT-NOTES.md#221-family--household-grouping).

> Status: **awaiting approval**. Do not start coding until the plan is approved.

---

## 1. Scope summary

Introduce a first-class household concept so pastors and treasurers can roll giving up by family without losing per-member fidelity. Adds two zone-scoped tables (`families`, `family_members`) with the same composite cross-tenant FK pattern as `members.ts` / `chapters.ts`, full CRUD under `/api/tenant/families`, a `family_id` grouping option on the member-statement and partnership-progress reports, a new **Top Family** report registered in `services/reports/registry.ts`, and SvelteKit surfaces under `/zone/families`, `/church/families`, and `/zone/members/[id]` (a "Household" panel). Maps Church Plus's `Family` + `Family Member` DocTypes and the `Top Family Report` (CHURCHPLUS-PORT-NOTES §2.2.1) and closes the Phase 10 exit checklist line "Family / household grouping shipped (zone-scoped `families` + `family_members`, household totals on the member statement, Top Family report)".

## 2. Data model

### 2.1 New tables

Two new files in `packages/db/src/schema/`, plus exports from `schema/index.ts`. Both follow the existing zone-scoped pattern: every row carries `zone_id`, every PK is `text` (uuid v4 via `crypto.randomUUID()`), and the composite `UNIQUE(zone_id, id)` guard is present so future cross-table FKs can use the `(zone_id, child_id) → (zone_id, id)` shape that already pins `members.ts` and `chapters.ts`.

**`families`** (`packages/db/src/schema/families.ts`):

```ts
families
  id                 text pk  default crypto.randomUUID()
  zone_id            text not null references zones(id) on delete restrict
  region_id          text     references regions(id) on delete set null    -- denormalised for reports
  chapter_id         text not null references chapters(id) on delete restrict
                                                                          -- families are chapter-scoped per CHURCHPLUS-PORT-NOTES §2.2.1
  reference_code     text not null                                         -- e.g. "F0000001"
  name               text not null                                         -- treasurer-curated label, e.g. "The Adeyemi household"
  primary_address_id text     references member_addresses(id) on delete set null
                                                                          -- household address; null means "use the primary member's primary address"
  notes              text
  metadata           jsonb not null default '{}'
  created_at         timestamptz not null default now()
  created_by_user_id text references users(id) on delete set null
  updated_at         timestamptz not null default now()
  updated_by_user_id text references users(id) on delete set null
  deleted_at         timestamptz                                            -- soft-delete; a deleted family preserves history for already-applied reports
constraints / indexes:
  unique (zone_id, id)                                                     -- composite FK target
  unique (zone_id, reference_code)                                         -- treasurer-visible code, unique per zone
  unique index (zone_id, chapter_id, lower(name)) where deleted_at is null  -- case-insensitive, soft-delete-aware
  index (zone_id, chapter_id) where deleted_at is null
  index (zone_id) where deleted_at is null
```

Reference codes use the same `text` shape as `chapters.reference_code` and `members.reference_code`, generated by a new `nextFamilyReferenceCode` helper (mirrors `nextMemberReferenceCode`).

**`family_members`** (`packages/db/src/schema/families.ts`, same file as the table is part of the same context):

```ts
family_members
  id                  text pk default crypto.randomUUID()
  zone_id             text not null references zones(id) on delete cascade
  family_id           text not null references families(id) on delete cascade
  member_id           text not null references members(id) on delete restrict
                                                                           -- restrict so we cannot lose a join row by hard-deleting a member;
                                                                           -- members are soft-deleted, so this never bites in practice
  relationship        text                                                 -- free-text per CHURCHPLUS-PORT-NOTES §5 (granularity = household, not kinship)
  is_primary_contact  boolean not null default false
  joined_at           date not null default now()
  left_at             date                                                 -- null = currently in family; set = archived membership row
  created_at          timestamptz not null default now()
  updated_at          timestamptz not null default now()
constraints / indexes:
  composite FK (zone_id, family_id) references families(zone_id, id)
  composite FK (zone_id, member_id) references members(zone_id, id)
  unique (zone_id, id)                                                     -- composite FK target for future reports / cross-refs
  unique index (member_id) where left_at is null                            -- a member belongs to at most one open family at a time
  unique index (family_id) where is_primary_contact = true and left_at is null
                                                                          -- exactly one primary contact per family (partial unique; CHURCHPLUS-PORT-NOTES §2.2.1)
  index (zone_id, family_id)
  index (zone_id, member_id)
  check  family_members_window_check  (left_at is null or left_at >= joined_at)
```

Notes:
- `relationship` is left free-text to match Church Plus's `Family Member` DocType; promoting to an enum is a v2 concern (open question §5 in CHURCHPLUS-PORT-NOTES already calls this out — "household for v1, kinship in v2").
- Composite cross-tenant FKs are present on **every** member/family reference. `family_members` carries `zone_id` not just for filtering but as the FK target column, so a row in zone A can never reference a member in zone B even if the application layer is bypassed. Both `members` and `chapters` already expose `UNIQUE(zone_id, id)` so the composite FK works without further schema changes.
- Soft-delete is allowed on `families` (a chapter may rename / fold a household and reports should keep working); `family_members` uses `left_at` to model the archived membership without losing history, mirroring `member_addresses.date_to`.

### 2.2 audit_events shape

Mutations write through `services/audit.ts` with the action codes below. All are tenant-scoped (`zone_id` set, action prefix not `platform.*`) so the existing `audit_events_zone_scope_check` CHECK is happy.

| action                       | entity_type | before / after                                              | reason field used         |
| ---------------------------- | ----------- | ----------------------------------------------------------- | ------------------------- |
| `family.create`              | `family`    | `null` / new row (sans timestamps)                          | optional notes            |
| `family.update`              | `family`    | old name/address/notes / new values                         | optional notes            |
| `family.delete`              | `family`    | full row / `null`                                           | required ("why")          |
| `family.member.add`          | `family`    | `null` / `{ memberId, relationship, isPrimaryContact }`     | optional                  |
| `family.member.update`       | `family`    | old `{ relationship, isPrimaryContact }` / new              | optional                  |
| `family.member.remove`       | `family`    | `{ memberId, joined_at, left_at, ... }` / `null`            | required ("why")          |
| `family.primary_contact.set` | `family`    | `{ previousPrimaryMemberId }` / `{ newPrimaryMemberId }`    | optional                  |
| `family.transfer`            | `family`    | `{ fromFamilyId }` / `{ toFamilyId, memberId }`             | optional                  |

These match the existing namespace convention (`contribution.*`, `chapter.*`, `administrator.*`); `services/reports/audit-log.ts` and the `/zone/audit` UI pick them up for free.

## 3. Migration plan

- **Migration number**: `0024_families_and_family_members.sql` (the latest committed migration is `0023_fix_skipped_retention_columns.sql`).
- **Generation**: `pnpm --filter @stewardledger/db exec drizzle-kit generate --name families_and_family_members` once the two new schema files land.
- **Inspection**: forbid any non-`numeric(19,4)`/non-`citext` accidental types; confirm partial unique indexes carry their `where` clauses through.
- **Backfill**: none. The feature ships disabled-by-absence (no rows = no households shown). Demo seed data (`scripts/seed-demo.ts`) gets a tiny opt-in `seedDemoFamilies()` helper so the three demo zones gain three to five sample households for review screenshots; production zones get nothing until a treasurer creates a family.
- **Legacy Church Plus mapping** (CHURCHPLUS-PORT-NOTES §5):
  - **Granularity question** ("household vs. kinship cluster"): **household for v1.** A family is chapter-scoped, has one current address (the family's primary contact's primary address, or `families.primary_address_id` when explicitly overridden), and a member belongs to one family at a time. Kinship clusters that span chapters or addresses become a v2 concern via a `family_links` table — explicitly out of scope here.
  - When a future ETL imports `Family` + `Family Member` rows, `Family.Address` maps to `families.primary_address_id` (resolved via the matching `member_addresses` row), `Family.Name` to `families.name`, and `Family Member.Relationship` to `family_members.relationship`. The `Family.PrimaryContactMember` field maps directly to the partial-unique `is_primary_contact` flag.
  - No ETL is being built in this PR; the mapping is documented in `docs/DOMAIN-MODEL.md §13` (table-mapping addendum) so a later migration tool has the conversion in writing.

Forward-only per `docs/ROADMAP.md` *Cross-phase practices*. Rollback is a paired `drop table family_members; drop table families;` migration we ship alongside as `0024_families_and_family_members.down.sql` — acceptable because no real data exists yet.

## 4. API surface

All routes under `tenantRouter` (mounted at `/api/tenant`) so they inherit `tenantMiddleware → requireSession → requireTenantAuth`. New file: `packages/api/src/routes/tenant-families.ts`. Service module: `packages/api/src/services/families.ts` (pure functions, takes `AuthorizedContext`).

### 4.1 Route table

| Method | Path                                                       | Role gate (read/write)                                       | Purpose                                                    |
| ------ | ---------------------------------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------- |
| `GET`  | `/api/tenant/families`                                     | read: any reader role (see §4.2)                              | List families in the caller's visible chapters.            |
| `POST` | `/api/tenant/families`                                     | write: `zone_owner`, `zone_admin`, `chapter_admin` (own chapter), `group_admin` (chapters in their groups) | Create family. Auto-generates `reference_code`.            |
| `GET`  | `/api/tenant/families/:id`                                 | read                                                          | Family detail incl. current members + ledger summary.      |
| `PATCH`| `/api/tenant/families/:id`                                 | write (same as create, chapter-clamped)                       | Update name / notes / primary address.                     |
| `DELETE`| `/api/tenant/families/:id`                                | write                                                         | Soft-delete (sets `deleted_at`). Cannot delete a family with open `family_members`. |
| `POST` | `/api/tenant/families/:id/members`                         | write                                                         | Add a member to the family. Fails 409 if the member is already in an open family. |
| `PATCH`| `/api/tenant/families/:id/members/:memberId`               | write                                                         | Update `relationship` / `is_primary_contact`. Toggling primary uses a single tx with the partial-unique guard. |
| `DELETE`| `/api/tenant/families/:id/members/:memberId`              | write                                                         | Set `left_at = today` (archive). Hard-delete only when the row was created in error (audit reason required). |
| `POST` | `/api/tenant/families/:id/transfer`                        | write (zone-tier only)                                        | Move all open members to another family. Audit emits one `family.transfer` event per moved member. |

### 4.2 Role gating

Reuses the existing predicates. No new role codes.

- **Read roles**: union of `REPORT_ZONE_READ_ROLES` (`zone_owner`, `zone_admin`, `zone_finance_admin`, `zone_auditor`, `zone_pastor_viewer`) + `REPORT_CHAPTER_READ_ROLES` + `REPORT_GROUP_READ_ROLES`. Implemented exactly as `tenant-members.ts` does today (constants `FAMILY_ZONE_READ_ROLES`, `FAMILY_CHAPTER_READ_ROLES`, `FAMILY_GROUP_READ_ROLES`).
- **Write roles**: `zone_owner`, `zone_admin`, `chapter_admin` (clamped to bound chapter), `group_admin` (clamped to chapters in their bound group). `chapter_treasurer` is intentionally read-only on this surface — households are an administrative concept, not a finance entry point.
- **Chapter clamp**: every write and the per-id read goes through the existing `requireChapterScope(ctx, family.chapter_id, FAMILY_ZONE_READ_ROLES)` helper from `packages/api/src/middleware/auth.ts`. Cross-zone family ids → 404, in-zone-but-out-of-scope → 403. Listing uses `visibleChapterIds(ctx, FAMILY_ZONE_READ_ROLES)` to clamp the SQL.
- **Access-check helper**: there is no separate `services/access.ts` file in the repo. The two existing chokepoints already do the job:
  - `packages/api/src/middleware/auth.ts` — `requireChapterScope`, `visibleChapterIds`, `hasAnyRole`.
  - `packages/api/src/services/reports/access.ts` — `REPORT_ZONE_READ_ROLES`, `reportVisibleScope`, etc., used by the report-side gate.
  - Family-write predicate lives at the top of `tenant-families.ts` next to the route definitions (matches the layout in `tenant-members.ts`).

### 4.3 Zod schemas

Added to `packages/shared/src/schemas.ts` (or a new `packages/shared/src/families.ts` if the file gets long). All wire-format money rules and uuid validation reuse the existing helpers.

```ts
familyCreateSchema = z.object({
  chapterId: uuidSchema,
  name: z.string().min(1).max(200),
  notes: z.string().max(2000).optional(),
  primaryAddressId: uuidSchema.optional(),
  primaryMemberId: uuidSchema.optional(),  // optional convenience: if set, add this member as primary in the same tx
});

familyUpdateSchema = familyCreateSchema
  .partial()
  .omit({ chapterId: true });                // moving a family between chapters is out-of-scope v1

familyMemberCreateSchema = z.object({
  memberId: uuidSchema,
  relationship: z.string().max(100).optional(),
  isPrimaryContact: z.boolean().optional().default(false),
});

familyMemberUpdateSchema = z.object({
  relationship: z.string().max(100).nullable().optional(),
  isPrimaryContact: z.boolean().optional(),
});

familyListQuerySchema = z.object({
  chapterId: uuidSchema.optional(),
  search: z.string().max(120).optional(),
  cursor: z.string().optional(),
  limit: z.coerce.number().int().min(1).max(200).default(50),
});

familyResponseSchema = z.object({ ... });    // mirrors the row + member list
```

Response payloads include a per-currency rolled-up giving total for the household (current ministry year by default, optional `dateFrom` / `dateTo` query params), computed at the service layer using the same `addMoney` helper from `@stewardledger/shared/money` that `services/dashboards/zone-dashboard.ts` already uses. No silent FX.

### 4.4 Service layer

`packages/api/src/services/families.ts`:

- `createFamily(ctx, input)` — picks the next `reference_code` via `nextFamilyReferenceCode`, inserts the row, optionally seeds the first `family_members` row as primary contact, audits.
- `addFamilyMember(ctx, familyId, input)` — enforces the "one open family per member" partial unique; pivoting `is_primary_contact` is done in the same tx as the insert when `isPrimaryContact = true` (sets the existing primary's `is_primary_contact = false`).
- `removeFamilyMember(ctx, familyId, memberId, reason)` — sets `left_at = today`. Rejects if it is the last open primary contact (operators must promote another member first); rejects if it would leave a family empty without `force = true` from a zone admin.
- `transferFamily(ctx, fromFamilyId, toFamilyId)` — moves every open `family_members` row from one family to another in a single tx, emitting one `family.transfer` audit row per moved member.
- `familyForMember(ctx, memberId)` — convenience used by `/zone/members/[id]` and the member statement to render the Household panel.

All write helpers go through `db.transaction` so partial-unique races surface as a clean 409 (`primary_contact_already_set`, `member_already_in_family`).

## 5. Report impact

### 5.1 New report — Top Family

- File: `packages/api/src/services/reports/top-family.ts`.
- Spec id: `top-family`. Title: `Top families`. Description: `Households ranked by total posted giving over a date range. Optional partnership-only mode.`
- Filters (Zod): `dateFrom`, `dateTo`, `chapterId?` (clamped via `reportVisibleScope`), `topN` (default 20), `partnershipOnly` (default false). Exactly the shape of `top-partners.ts`, swapping the join target from `members` to `families` via `family_members`.
- Joins: `contribution_lines → contributions → members → family_members (where left_at is null) → families`. Reversal contributions net to zero (status filter `('posted','reversed')` matches the existing top-partners contract).
- Output columns: rank, family ref, family name, chapter ref, chapter name, currency, total. Excel + PDF via the existing branded-table renderer; per-currency subtotals.
- Registered alongside the existing thirteen specs in `services/reports/registry.ts` (one push to the `REGISTRY` array). The UI lights up automatically because the picker reads `listReports()`.
- Legacy mapping (REPORTS.md style): `Givings_Family_TopPartner` / Church Plus `Top Family Report`.
- Access check: same as `top-partners.ts` — zone readers unconstrained, chapter/group readers clamped to `reportVisibleScope`.

### 5.2 Existing reports — `family_id` grouping option

The treasurer wants to drill in two ways: (a) "show me families ranked by giving" (the new Top Family report) and (b) "give me the existing member statement but with the household total at the top". Two existing specs gain a `family_id` filter:

| Report                          | File                                                      | New filter                                                  | Effect                                                                            |
| ------------------------------- | --------------------------------------------------------- | ----------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Member statement                | `services/reports/member-statement.ts`                    | `familyId?: uuid` *or* `groupBy?: 'member' \| 'family'`     | When `groupBy = 'family'`, switch the fetch to roll up by family + currency and render a "Household summary" section at the top of the PDF / Excel. When `familyId` alone is supplied, restrict rows to members currently in that family. |
| Member finance summary          | `services/reports/member-finance-summary.ts`              | `groupBy?: 'member' \| 'family'`                            | Family grouping pivots by household, summing each member-line into the household row. |

These are additive filters (default behaviour unchanged); the existing golden-file tests stay green. The new behaviour is covered by added golden files (§7.3).

A "household total" line is also added to the member-statement PDF *header band* whenever the rendered member belongs to a family — that's the line CHURCHPLUS-PORT-NOTES §2.2.1 calls out specifically ("household totals on the member statement").

### 5.3 Partnership progress — left untouched in v1

Partnership progress is keyed off `financial_targets` (chapter × giving_type × ministry_year). Households don't appear in that grain in Church Plus either; deferring family-level partnership rollups keeps the scope small. Documented as an explicit non-goal (§8).

## 8. Out of scope (explicit non-goals)

1. **Kinship clusters / cross-chapter families.** A member belongs to one chapter, and a family lives in one chapter (CHURCHPLUS-PORT-NOTES §5 calls this out — v2 concern).
2. **Family-level partnership targets.** `financial_targets` stays keyed by chapter × giving_type × ministry_year. No `family_id` column on `financial_targets`.
3. **Family-level imports.** The bulk slip / envelope importer (Phase 10 §2.2.3 in CHURCHPLUS-PORT-NOTES) is a separate PR; this PR does not change the import pipeline.
4. **Family-level RBAC.** Families do not gain their own role bindings; access is derived from chapter + group bindings.
5. **Custom relationship taxonomy.** `relationship` is free-text. Promoting to an enum + dropdowns is a v2 follow-up.
6. **Auto-detection / dedup.** Nothing in this PR proposes families based on shared address or surname. A future "family merge proposal queue" (mirroring `member_merge_proposals`) is post-v1.
7. **PDF letter template changes** beyond inserting the household summary band on the existing member-statement PDF. The bespoke letter-style member-statement work tracked in Phase 7 stays on its own branch.

## 9. Risks and rollback

- **Risk: composite FK omitted on a downstream table.** Mitigated by the `families.test.ts` cross-tenant FK assertion in §7.4 — drizzle would surface the missing constraint as a failing test.
- **Risk: partial unique indexes drop in production.** Drizzle's `where` clauses do ship in the generated SQL; we still eyeball the generated `0024_*.sql` for `WHERE` predicates (§3 inspection step).
